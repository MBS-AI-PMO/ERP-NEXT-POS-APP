# TillPOS 1.1 Implementation Plan

**Goal:** a refused bill never holds the upload queue; money decimals 2/3 as a supervisor setting; newest scanned line on top.
**Spec:** `docs/superpowers/specs/2026-10-16-tillpos-1.1-queue-decimals-latest-scan-design.md`
**Execution:** native (owner asked to build, test on dev and release both packages).

Dev spike (2026-10-16, Test Counter, developer key) confirmed: a closing keeps the till's totals when a bill is missing from
`pos_transactions`; a bill linked to a closed shift is refused ("POS Shift … is not open"); the same bill linked to a newer open
shift is accepted with its old posting date/time; `PUT /api/resource/POS Invoice/<draft>` rewrites a draft (items, shift) and it
then submits; the newer shift's closing consolidates the late bill.

## Global constraints
- `dotnet test -m:1` green after every task; TreatWarningsAsErrors.
- Never send a bill twice: client-id lookup first (unchanged); only this till's own drafts (`posa_client_request_id`) are rewritten.
- Network / auth / unknown outcomes still stop the run (unchanged).

## Task 1 – Writer can update a document
- `IErpWriter.UpdateAsync(doctype, name, doc)` → `PUT /api/resource/{doctype}/{name}`; `ErpWriter`, `NoWriteErpWriter` (throws), `FakeErp` (records `Updated`, merges into the stored row, `RejectUpdate`).
- Tests: ErpClient sends PUT with the body; NoWrite refuses.

## Task 2 – Uploader: a failed bill does not hold its shift's closing
- In `ShiftAsync`, a bill that is not in ERPNext after its attempt is **parked** when its status is Failed, or when it is a return whose original (this till) is Failed; otherwise it is **waiting**.
- The closing waits only for waiting bills. A closing sent with parked bills adds a run note.
- Tests: refused bill → closing sent, next shift opening + bills sent; in-flight bill → closing waits; return of a parked sale → closing still sent.

## Task 3 – Uploader: late bills go with the counter's current shift
- If a shift's closing is Synced/Handled (or it was just sent), its remaining bills use the ERPNext name of the counter's current open shift on this till (opening Synced, closing not final, same POS Profile, latest); none → note "waits for the next shift of <counter> to open in ERPNext".
- Tests: retry after closing → payload `posa_pos_opening_shift` = newer shift, posting date unchanged; no open shift → waits, sent after the next opening.

## Task 4 – Uploader: a found draft is rewritten before submit
- Live, invoice, lookup finds this till's draft → mark in flight → `UpdateAsync` with the freshly built payload (current shift link, till's lines/payments) → totals check → submit. Refused update → Failed with ERPNext's message.
- Tests: draft exists → Updated once, no second insert, submitted; refused update → Failed.

## Task 5 – Closing payload: full shift VAT/quantity, late bills listed
- `ClosingShiftPayload.Build` takes all the shift's receipts (taxes, total_quantity) and the transactions list.
- `pos_transactions` = the shift's uploaded bills + submitted POS Invoices in ERPNext linked to that opening (`posa_pos_opening_shift`), de-duplicated (read-only query; skipped for DryRun stand-ins).
- Tests: VAT = whole shift incl. parked bill; a late bill linked to the shift appears in its closing list once.

## Task 6 – Money decimals setting
- Setup dialog: "Money decimals: 2 / 3" (TillSettings.Precision); disabled with a note while a shift is open (`IDialogs.ShowSetupAsync(..., shiftOpen)`).
- Tests: settings round-trip keeps Precision; login passes shiftOpen.

## Task 7 – Newest scanned line on top
- `SaleViewModel` shows lines newest-touched first (scan, search, quantity change, re-scan moves to top) and selects the top line after an add; cart/receipt order unchanged.
- Tests: order after adds/re-scan; receipt order unchanged; selection = top.
